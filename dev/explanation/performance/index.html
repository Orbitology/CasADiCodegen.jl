Compile and run times of the generated code

This page gives the measurements behind the defaults of the package, whose conditions are in Package versions used to build this manual: compile time at the first call, which grows with the model, and run time at later calls, which depends on the form of the code.

Run time of the in-place, out-of-place and static forms

An instruction is one operation as CasADi counts them: a scalar operation in an SX function, a graph operation such as a matrix product or a call in an MX function. Scalar code, from an SX function or an expanded MX function, allocates nothing in place or out of place with static arrays, whatever its size; matrix code is described in Scalar code, matrix code and special CasADi functions. Two scalar models with their 6 by 6 Jacobians, measured once on Julia 1.13:

The first call is mostly compilation. For scalar code above about 50,000 instructions, or matrix code above about 1,000, see Speed up compilation of large models.

How `g!` checks the pattern of a sparse matrix

With a SparseMatrixCSC, g! compares the whole pattern of a matrix whose index vectors (colptr and rowval) are not those of the last matrix that passed this comparison; otherwise it compares the number of rows and of stored values only, so a call costs as much as the function on nonzeros.

Compile and run time of a split function

Above split_above instructions, build_function and generate_julia split the code into sub-functions of at most chunk_size instructions (see Speed up compilation of large models). The defaults rest on the measurements below, made once on Julia 1.13 for the function on nonzeros of two models with dense Jacobians: a chain of maps, each applied to the result of the one before, and the acceleration of 40 bodies under mutual gravity.

Once a function is split, the sub-function size barely affects later calls, which the split makes 15 to 40 percent slower, while the first call slows as the size grows. Whether splitting shortens the first call depends on the model: the largest chain compiles in 54 s instead of 339 s, while the gravity model gains nothing at the default size. Smaller versions of the two models near the default limit of 50,000 instructions, not in the table, took 18 s and 14 s unsplit against 10 s and 22 s split.

Solver compile time for each new model

With the default specialize = SciMLBase.FullSpecialize of the SciML constructors, OrdinaryDiffEq.jl compiles its solver again for each new model. specialize = SciMLBase.AutoSpecialize reuses it for a Vector{Float64} state; an explicit solver such as Tsit5() reuses it only with jac = false. On Lotka-Volterra and then the Lorenz system, the first solve of the second model took the times below, and each later solve was 5 to 20 percent slower:

First solve of the second modelFullSpecializeAutoSpecialize
Rodas5P()2.55 s0.15 s
Tsit5()0.89 s0.08 s, with jac = false

Compile and run time of scalar and matrix code

A model that calls a scalar function of 710 instructions 20 times in a chain, and returns the result with its Jacobian, shows the cost of expansion: expanded code repeats the 710 instructions at each call, so it builds and compiles longer and here also runs slower than matrix code, which compiles the called function once. Both are faster than the CasADi virtual machine; one measurement of each:

expand = true4.8 s86 s183 µs
